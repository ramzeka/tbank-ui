Здесь зафиксировано состояние до исправлений. Повторная проверка описывает изменения в локальном прокси и UI и границы проверки однократного исполнения. [Исправления после аудита](../tests/qa/README.md#исправления-после-аудита-безопасности)

В текущем коде выявлены **три замечания приоритета P1 и четыре замечания P2**. До работы с реальными средствами следует закрепить доверенный адрес прокси, сделать ошибки HTTP приоритетными при обработке ответа и подтвердить серверную защиту от повторных финансовых операций. На моках также подтверждено, что отдельные закрытые формы сохраняют введённые данные после завершения сеанса.

## Объект и метод проверки

Проверены текущая рабочая копия поверх `53a2475`, браузерный код `dist`, запуск на Windows, локальный PowerShell-прокси и тестовый стенд `tests/qa`. Использованы анализ кода, полный прогон на синтетических данных и отдельная проверка остаточных данных форм. Edge 158.0.4370.33 работал в отдельном тестовом профиле. Тестовый прокси добавляет ограничение на отправку запросов только мок-серверу, поэтому политика адресов штатного прокси оценена по коду. [Настройка тестового прокси](../tests/qa/harness.mjs#L36)

**P1** означает приоритет до выпуска с реальными средствами из-за возможного раскрытия токена или нарушения целостности финансовой операции. **P2** означает риск для конфиденциальности и изоляции с более узкими условиями возникновения. Приоритеты учитывают назначение приложения и границы проверки.

## Выводы P1

### A01 Отправка токена на настраиваемый адрес прокси

**Статус — подтверждено по коду, влияние зависит от конфигурации.** UI проверяет схему URL и сохраняет его в настройках. Локальный прокси получает адрес назначения из заголовка запроса, допускает произвольный HTTPS-узел за пределами исключений и допускает HTTP на другом порту `127.0.0.1`. Затем он отправляет выбранному узлу исходный `Authorization` и данные операции. Ошибочный или подменённый адрес может раскрыть токен и данные получателю запроса. Для такого сценария нужен доступ к настройкам или локальному контексту запроса. [Проверка URL в UI](../dist/app.js#L76) · [Выбор адреса в прокси](../server.commands#L121) · [RFC 6750, защита Bearer-токена](https://www.rfc-editor.org/rfc/rfc6750.html#section-5.2)

**Критерий исправления.** Для боевого режима адрес назначения задаётся администратором и проверяется прокси до отправки токена. Незарегистрированный адрес отклоняется. Loopback HTTP доступен в изолированном режиме моков. Боевые токены имеют ограниченную аудиторию, срок действия и набор прав. [RFC 9700, ограничение прав токенов](https://www.rfc-editor.org/rfc/rfc9700.html#section-2.3)

### A02 Ошибка HTTP может стать успехом в интерфейсе

**Статус — подтверждено по коду, реальный шлюз требует проверки.** `methodResponse()` берёт `responseCode` из JSON независимо от транспортного HTTP-статуса. При противоречии верхний `401` может потерять обработку завершения сеанса, а HTTP-ошибка с кодом успеха в теле может стать подтверждением записи и удалить локальный ключ повтора. Текущие тесты подтверждают штатную обработку ошибок, которые шлюз передаёт внутри успешного HTTP-ответа. [Разбор ответа](../dist/app.js#L298) · [Завершение сеанса и удаление ключа](../dist/app.js#L422)

**Критерий исправления.** При HTTP-ошибке интерфейс сохраняет соответствующий класс результата и закрывает сеанс при `401`. Код внутри тела уточняет результат при успешном HTTP-ответе по договорённости с прокси. Противоречивый ответ не подтверждает мутацию. Ключ незавершённой операции сохраняется для сверки.

### A03 Защита платежей от повторной регистрации зависит от вкладки

**Статус — граница клиентской защиты подтверждена по коду и штатным тестом.** Ключ платежа или перевода сохраняется в `sessionStorage`. После потери ответа и перезагрузки той же вкладки тесты подтверждают один ID и одно списание. Другая вкладка или новый браузерный сеанс может начать с пустого журнала ключей. Флаг неизвестного результата повтора выплаты также хранится в памяти. Сверка идентификации проверяет присутствие операции в списке. Первый запрос в этот момент может ещё обрабатываться. Фактический риск второго проведения зависит от гарантий внешнего шлюза и T‑API. [Журнал ключей](../dist/app.js#L329) · [Повтор выплаты](../dist/app.js#L604) · [Сверка идентификации](../dist/identify.js#L230) · [WHATWG, область sessionStorage](https://html.spec.whatwg.org/multipage/webstorage.html)

**Критерий исправления.** Шлюз ведёт устойчивый идентификатор намерения и атомарно предотвращает его повторную регистрацию. Оператор может получить статус по идентификатору операции после разрыва сеанса. На интеграционном стенде подтверждается однократное исполнение после неизвестного результата, при параллельной обработке и при смене вкладки, профиля и оператора. Отдельно проверяются повтор выплаты, завершение этапа и идентификация пополнения по гарантиям их API.

## Условия проверки боевого контура

Корпоративный шлюз и банк определяют права на конкретный счёт, бенефициара, платёж, сделку и этап. Локальная проверка UUID подтверждает формат идентификатора. Для заключения о доступе нужны интеграционные проверки минимум с двумя операторами, двумя счетами и ролью только для чтения, включая запрет операций с недоступными объектами. В этот же прогон входят валидация токенов, TLS и mTLS, сроки действия ключей, сверка асинхронных платежей и наличие журнала операций без токенов и полного тела запроса. Прогон аудита использовал синтетические данные и локальный мок. [Граница прокси в проекте](../README.md#как-проходит-запрос) · [OWASP, авторизация на уровне объектов](https://api-security.owasp.org/editions/2023/en/0xa1-broken-object-level-authorization/)
